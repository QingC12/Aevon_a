## 一、已定位问题和本轮修正

### 内容自动重排：恢复独立场景尺寸适配

31 删除旧 SthenoKeyboard 时，连带移除了非键盘职责的 UIScreen bounds 兼容。这会影响依赖该 API 按浮窗场景宽高布局的应用，与用户报告的抖音重排回退高度吻合；没有把静态证据写成已取得抖音调用栈的唯一根因证明。

32 新增独立 AppSceneReflow，不恢复整枚旧键盘库。条件满足时，应用读取主屏 bounds 会得到当前原生 UIWindowScene、当前方向的 `_boundsForInterfaceOrientation:` 结果：

- 沿用原 Inject 和全局 SettingMask bit31（原窗口比例/尺寸适配选项），**不强行改用户设置**。
- 开关由 SpringBoard 随同原子布局快照转送，避免依赖应用访问另一偏好域的能力；客户端场景策略在生命周期、场景 diff 和布局事件刷新。
- 只作用于新鲜的真实浮窗成员、主屏、单一明确的前台 key-window scene；全屏同尺寸、断连、多场景歧义等回原生。
- 返回原生 scene 尺寸，不硬编码抖音尺寸，不乘视觉 card scale，不重写场景 frame。
- 接收 scene diff 前刷新策略，再原样调用 UIKit 原方法，读取 scene 时不沿用旧全局实例缓存。
- 不引入旧键盘 window frame/transform、通知改写器或 URL 钩子。

键盘几何显式读取保存的原 UIScreen bounds IMP，不会因内容重排的虚拟 bounds 而把物理屏幕误当 731 高。重排日志包含 enabled、bit31、hosted、scene 和 unmodifiedScreen，便于真机核对该兼容路径是否启用。

### 键盘：只允许 SpringBoard 实际采样成为物理事实

31 的源码允许 app notification frame 进入 request，再优先覆盖宿主物理缓存；客户端即使已有 host layout，也继续使用 app raw 做映射。双缓冲只保证数据一致，没有认证坐标来源。

用户日志中，L24 记录 `(0,590,430,342)`，约 0.906ms 后 L25 却使用 `(0,774,430,158)`。同一卡片下映射量分别为 241.5 和 57.5，相差184。这说明来源分歧会显著改变遮挡量，不是应加入一个184点偏移。**旧日志没有独立SB来源标记，因此590/342在回归中是明确声明的权威场景，而不是谎称日志已经证明它是真实物理真值。**

32 已修正端到端选择：

1. 只有 SB 的物理通知入口可以写入物理键盘 frame、visible、generation。请求、续租、恢复以及 layout 回读都不能改它。
2. App 请求表达输入归属，几何不再作为 SB 权威；有效、无效、屏外等 raw 都只作该映射路径的诊断，不再用形状校验结果决定宿主物理隐藏/显示。
3. Client 用同一代 host.card + host.keyboard 映射场景，并供 inset 与规范通知共同使用；没有权威时不拿 app raw 猜SB物理帧。非 hosted / 原生全屏的正常系统行为保留。
4. SB 收起后，旧请求、新的 app claim、续租均不能复活物理键盘或触摸排除。
5. 独立复查还发现“SB 已 hidden，但客户端原生 fallback 继续透传旧正帧/正 inset”的消费漏洞。最终版已区分 unknown 与已知 hidden：对目标浮窗交付 canonical empty，scene inset 明确为0；非浮窗/全屏仍保留 native fallback。新的正常显示必须等待新的 SB generation/visible。
6. 49项原有源码/脚本/资源按31基线保护；无输入框、背景条、工具栏、祖先的 transform/frame/bounds/contentInset/safeArea 写入，无 App 专属固定偏移。
