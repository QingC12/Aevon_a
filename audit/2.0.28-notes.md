## 一、搜索：不再依赖原版界面的目录缓存

### 确定的代码证据

原版 GlobalEnv 构造函数 `0x84110` 将应用缓存字段设为 Swift 空数组；用户/系统目录在另一个异步 UI 任务中通过 `0x24fe8` 枚举，再写入 `+0x18 / +0x20`。2.0.27 的选择器只 retain 这两个共享缓存，成功读到 `[]` 就会把它固定为本次面板的数据源。因此共享对象存在并不等于已取得完整的已安装应用目录。

这证明存在“原版目录尚未填充时搜索恒为空”的路径，不能单凭本次用户描述认定它是设备上唯一的失败原因；文本输入是否实际到达仍需实测。

### 本版修改

- 面板取目录时调用原版已有的 `0x24fe8` 枚举函数，分别传 user=0、system=1，取得新的原生 App 数组，不再读 GlobalEnv 的初始空缓存。
- 继续复用原版隐藏/禁止启动等过滤规则，不伪造 LaunchServices 应用对象，不调用 GlobalEnv 初始化或原偏好恢复任务，不改用户设置。
- 仍通过当前 pinned managers 排除已加入圆盘的应用，去重并排除截图/录屏虚拟项；点选提交前仍重新检查成员资格及固定状态。
- 不在每个键入事件中重新枚举。显示的是本次打开时的快照，搜索谓词仍为原有的中文/显示名及 bundle ID 子串匹配，并保留大小写、重音、全半角处理。
- 无可选应用与搜索未匹配使用不同空状态文案。已有圆盘应用不出现在此面板是原设计，不将其改为全量显示。
- UITextField 编辑回调、SwiftUI query 绑定和 IME marked text 处理未改动；没有把所有搜索问题都归因于字符串匹配，也没有因这次反馈宣称键盘已验证正常。

## 二、放大顿帧：去掉确定重复的同步工作

2.0.27 在一次 IPC 首帧回调中，先解析 owner 和 frame，再进入几何协调重新扫描同一批浮窗并读取归属；首个布局发布又连续执行一次几何刷新/键盘视图扫描，随后立即 tick 重复相同工作。这些是实际存在的主线程重复工作，但尚无目标设备分段耗时，不能说已测定顿帧全部由此造成。

本版：

1. 一次一致快照同时取得归属和可用物理帧；只需要归属时不读取无用帧通道，仍保留前后提交字/owner 校验及原有时效条件。
2. 已在当前同步 IPC 回调中取得的 +1 model 仅在该次调用内借用，不重新枚举；真实原生通知仍独立核验，没有跨事件缓存模型来跳过有效性检查。
3. 重复相同候选不再重建 prepared preview；新输入会话、最小化与关闭清理仍保留。
4. 首个布局目标只刷新一次几何，优先使用同次 Will 已经校验的键盘帧，不在动画首帧再遍历键盘窗口视图。确无有效帧时保留受限回退测量。
5. 初次采样结束即返回；下一次采样交给已有 timer，不在同一调用栈马上再做一次。未缩短 timer、稳定采样阈值或 preview 超时。

没有更改原版弹簧参数、放大目标数学、还原快照、原生 show/hide 次数、内容手势、停靠、应用编辑器保护或面板输入隔离。本版不声称有已测量的帧率/内存提升，也不把主机计数测试当作真机流畅度测试。
